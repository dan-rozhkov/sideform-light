# Scheduled chats — design

Date: 2026-11-15. Status: decided in autopilot (`/auto`); the calls below are the builder's, open to correction.

## Intent

The person wants the agent to do a browser job on its own at set times: "every weekday at 9:00 check the
prices on these three shops and tell me what changed", "every hour look at the status page". A schedule is
a prompt plus a cron time. When the time comes, the running app opens a new chat in the agent panel with
that prompt, and the ordinary browser agent (`agentMode: "browser"`, `browse_agent`, isolated sessions,
saved logins, traces) does the work. The person sees the result as an unread chat in the chat list.

## Goals

- Create, edit, switch on/off, delete schedules; "Run now"; see the next run and the last run, open the
  chat of the last run.
- A run is an ordinary chat: visible, steerable (the person can answer the agent's question, stop it, write
  a follow-up). It never takes focus or switches the active chat (same rule as MCP tasks).
- Cron expressions (standard 5 fields, local time) with easy presets in the UI.
- Survives restarts: schedules are stored on disk by the shell.

## Non-goals (v1)

- Running while the app is closed (no OS-level launch agent, no cloud runner). The app must be running.
- Catch-up of runs missed while the app was closed or the machine slept: they are skipped.
- An agent tool to create schedules from the chat ("remind me every day…"): needs a backend tool contract;
  later.
- Per-schedule model choice, notifications outside the app, result delivery anywhere but the chat.

## Anti-goals

- A schedule must not pile up runs: a run never starts while the previous run of the same schedule is still
  running or waiting for an answer.
- A scheduled run must not hijack the panel or the active chat.
- No new network surface: everything is local IPC.

## Approaches considered

- **A. Scheduler in Electron main, runs are panel chats over the existing main→panel task channel
  (chosen).** Main owns the store (`<userData>/schedules.json`, like `mcp-bridge.json`) and the clock; at
  the time it sends the panel a request on the MCP panel channel (`mcp:task-request`, which the panel
  registers always, not only when the MCP server is on). One agent implementation; the scheduler keeps
  ticking while the panel reloads.
- B. Scheduler in the panel page (timers + localStorage). Rejected: the Settings tab is a different page,
  the schedule list would live in browser storage, a panel reload drops timers.
- C. OS cron / launchd starting the app. Rejected for v1: platform-specific, starts a window unasked.

## Design

### Cron (app/src/main/schedules/cron.ts)

Five fields `minute hour day-of-month month day-of-week`, local time. Each field: `*`, a number, `a-b`,
`*/n`, `a-b/n`, `n/s` (from n to max), comma lists. Month names `JAN..DEC` and day names `SUN..SAT`
(case-insensitive) are accepted; day-of-week 7 = Sunday. Day-of-month and day-of-week both restricted
(neither is `*`) → a day matches when EITHER matches (Vixie cron). Expression length ≤ 100. Exposed:
`parseCron(expr) -> { cron } | { error }`, `cronMatches(cron, date)`, `nextRunAfter(cron, date) -> Date | null`
(searches up to ~5 years ahead; null when it never fires, e.g. `0 0 31 2 *`).

### Store (`<userData>/schedules.json`, 0600, atomic write)

```ts
interface Schedule {
  id: string;            // ^[A-Za-z0-9_-]{1,128}$, generated by main
  name: string;          // 1..100 (trimmed)
  prompt: string;        // 1..20000 (trimmed non-empty)
  cron: string;          // valid per parseCron
  enabled: boolean;
  createdAt: number; updatedAt: number;
  lastRun?: { at: number; status: "started" | "skipped" | "failed"; chatId?: string; error?: string };
}
// file: { version: 1, schedules: Schedule[] }   max 50 schedules
```

A broken file → empty list (logged), never a crash; a bad entry is dropped on load.

### Scheduler (app/src/main/schedules/scheduler.ts)

- Ticks every 15 s (injectable clock/timer, `unref`). For each enabled schedule whose cron matches the
  current local minute and that has not fired in this minute (in-memory key; on start seeded from
  `lastRun.at`), it fires.
- Fire = `panel.request({ op: "schedule-start", scheduleId, prompt, title, previousChatId })`.
  `title` = `<name>` (the panel keeps it, no auto title). Reply `{ task }` → `lastRun = { status:
  "started", chatId: task.taskId }`; `{ error }` → `lastRun = { status: "skipped" or "failed", error }`:
  "skipped" when the panel says the previous run is still running or the run cap is reached
  (`code: "busy"` in the reply), "failed" otherwise (no window, offline, …).
- "Run now" fires the same way regardless of `enabled` and of the minute.
- Waking from sleep: only the current minute can fire; earlier ones are gone (no catch-up).

### Main → panel ops (added to the existing `McpPanelRequest` union)

```ts
| { op: "schedule-start"; scheduleId: string; prompt: string; title: string; previousChatId?: string }
| { op: "open"; taskId: string }   // activates that chat in the panel and shows the panel; { ok: true }
```

`schedule-start` in the panel: validate (prompt 1..20000, title ≤ 200); offline → `{ error }`; if
`previousChatId` is a chat whose status is `running`/`needs_answer` → `{ error: "The previous run is still
running", code: "busy" }`; if 3 schedule runs are already executing (busy or launch queued) → `{ error: "...", code: "busy" }`;
otherwise `createChat({ activate: false, source: "schedule" })`, set the title, queue the prompt, mark
unread, reply `{ task }` (same `TaskState` as `start`). The reply type gains the optional `code: "busy"` on
the error shape. MCP `start`/`get`/`list`/… keep seeing only `source: "mcp"` chats.

Chat meta `source` becomes `"mcp" | "schedule"` (`chats:save|read|list`; anything else is still rejected).
Browse traces: a schedule chat counts like an MCP task for the "Record traces" setting (default mode
records them); the option label becomes "QA tests, MCP and scheduled tasks".

### Settings page (`penDesktop.schedules`, channels `schedules:*`)

Answered only to the top frame of a Settings tab on the settings page (same guard as `mcp-settings:*`),
else `{ error: "Not allowed." }`.

```ts
interface ScheduleView extends Schedule { nextRunAt: number | null }
interface ScheduleInput { id?: string; name: string; prompt: string; cron: string; enabled: boolean }
schedules: {
  list(): Promise<{ schedules: ScheduleView[] } | { error: string }>;
  save(input: ScheduleInput): Promise<{ schedule: ScheduleView } | { error: string }>; // no id = create
  remove(id: string): Promise<{ ok: true } | { error: string }>;
  runNow(id: string): Promise<{ schedule: ScheduleView } | { error: string }>;      // after the fire
  openChat(chatId: string): Promise<{ ok: true } | { error: string }>;              // op "open" to the panel
  onChanged(cb: () => void): () => void;   // `schedules:changed` pushed to Settings tabs after any change/fire
}
```

New settings section `"schedules"` (label "Schedules", clock icon), valid in `settings:open` and in the
Settings URL. The agent panel's menu gets "Scheduled tasks…" which opens that section.

### UI (ui/src/components/settings/sections/SchedulesSection.tsx)

- Header copy: what a schedule does and that the app must be running.
- List: name, human frequency ("Every weekday at 09:00", or the raw cron), next run (relative + absolute),
  last run (status, relative time, "Open chat"), on/off switch, Run now, Edit, Delete (inline confirm, no
  `window.confirm`).
- Editor (create/edit inline): Name, Task (textarea, what the agent should do), Frequency: preset select
  (Every hour at :MM, Every day at HH:MM, Weekdays at HH:MM, Weekly on <day> at HH:MM, Custom cron) with
  the fields it needs; Custom shows a cron input with a short syntax hint. Save shows main's validation
  error inline. Empty state with a "New schedule" button.
- Chat list in the panel: a schedule chat shows a small clock icon before the title.
